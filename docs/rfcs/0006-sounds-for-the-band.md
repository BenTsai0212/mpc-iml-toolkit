# RFC 0006: Sounds for the band

- Status: Proposed
- Date: 2026-11-26
- Related: RFC 0002, RFC 0005, #262, #266

## Summary

The band (`ensemble`, RFC 0005) sends MIDI. What it sounds like depends on
instruments the musician sets up by hand in the DAW. This RFC proposes an optional
feature of this repository that turns recordings of single notes into a **kit**:
one SFZ instrument for each band part, drum hits, and a manifest that records how
each file was made and measured. A kit plays in any SFZ player on the band's
tracks. Words change what the band sounds like, never what it plays.

Generating the single notes with a model the musician has installed is an optional
step before playing, in the same way that RFC 0002 made LLM mapping an optional
feature that uses the user's own model.

## Problem and users

The users are the same as in RFC 0005: musicians who play a little and want to
improvise with the band, starting from something that sounds good at once.

On 2026-11-25 the musician played the band with content and sounds chosen for each
style. It sounded much better, and the band's changes could be heard. With
instruments built from generated single notes, the lo-fi set (#262) fitted the
style better than with general-purpose sounds. All of that was done by hand: single
notes for each instrument were measured, selected, trimmed and mapped across the
keyboard. That work is slow, easy to get wrong, and not recorded anywhere, so a
good result cannot be repeated or compared.

The first scope rule of RFC 0005 does not allow a new interface for this. Three
options were considered (#266):

| Option | What it means | Why not chosen |
| --- | --- | --- |
| 1. Leave sounds outside the toolkit | Only document how to set up instruments in the DAW | The manual work stays manual and unrecorded |
| 2. A separate practice repository | The tool depends on toolkit internals (the offline replay of the band, the list of built-in sets, the engine's controls) through a version pin | Those internals change often; a pin would break or hold the tool back |
| 3. An optional feature of this repository | Like LLM mapping in RFC 0002 | Chosen |

## Proposal

### What it is

- **Input:** recordings of single notes (recorded by the musician, or generated by
  an optional step), one or more for each instrument.
- **Output, a kit:**
  - one SFZ instrument for each band part (bass, melody and chords);
  - drum hits;
  - a manifest that records, for each file, where it came from (recorded, or the
    model, prompt, seed and settings that made it), how it was measured and why it
    was chosen.
- **Where it plays:** in any SFZ player, on the tracks the band already plays. The
  toolkit does not play audio.
- **What words change:** a description of the sound of each player changes which
  notes are made or chosen. It never changes the notes, rhythms or controls the
  band plays.

### What to build, in order

Each step goes through its own Issue.

| Step | What |
| --- | --- |
| 1 | Measure a note and build an instrument: pitch on the sustain, the share of energy on harmonics, one note for each pitch, key ranges split halfway between the chosen notes, an SFZ file and a manifest |
| 2 | Audition: render offline what the band plays with a kit, each part alone and all together |
| 3 | A tab in the web demo: choose a built-in set, describe the sound of each player, listen, keep or try again, and set the band to that set with the existing controls |
| 4 | Generation as an optional step that calls a model the musician has installed (first: the open weights of Stable Audio 3, through its own command), before playing only. Prompts, seeds and settings go in the manifest |
| 5 | One command that makes a whole kit |

Steps are ordered by dependency. Each step that changes what the musician hears is
played and recorded as in RFC 0005.

### Rules

- **Two interfaces only.** This RFC lifts the first scope rule of RFC 0005 for
  exactly two interfaces: one tab in the web demo (step 3) and one command
  (step 5). There is no protocol change; the tab sets the band through the existing
  `bass-loop`, `loop` and `progression` controls.
- **No models in the toolkit.** The toolkit does not bundle, download or host
  models or weights, and holds no keys. The musician installs the model and accepts
  its licence.
- **Audio stays local.** Generated or recorded audio and kits stay on the
  musician's machine and are never committed or uploaded. Tests use synthetic
  tones.
- **Optional dependencies.** New dependencies are an optional extra (`soundfile`;
  `numpy` is already in `demo`). The core install does not change.
- **A person listens.** A person listens before a kit is kept. Measurements catch
  obvious problems (wrong pitch, noise, silence), not everything.

## Non-goals

- Generating notes or anything else the band plays.
- Generation while playing.
- Audio-to-audio (transforming the musician's audio).
- A sampler inside the engine.
- Instrument formats of a specific DAW.
- A plugin (a later front end).
- Everything listed as a non-goal in RFC 0001 to RFC 0005.

## Phases and gates

This RFC stays within the phase of RFC 0005 (Epic #113).

- Gate: starting from single notes for one built-in set, a musician gets a kit,
  loads it in Live and plays it with the band, and the result is recorded under the
  trial procedure (`docs/trials.md`).

## Open questions

- How to loop sustained sounds (pads, keys held over a bar or more).
- How to check that the notes of one instrument sound alike (level, brightness,
  attack), beyond pitch and harmonics.
- Whether drum hits are an SFZ file as well, and how they map to pads.
- Which other models, and how to add them without changing the rules above.
